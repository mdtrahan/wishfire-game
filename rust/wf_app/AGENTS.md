# Rust app DOX (wf_app)

## Purpose
- The browser game as one Rust binary: macroquad client (ported from the slice `wf_client` at 9c142b5f) over `simulation_core::combat_abi::World`, the typed combat host.

## Contracts
- The sim is authoritative. `game.rs` owns one `wf_host::Session` (30 Hz pacing, stage director, rewards, save) and the client reads `Snapshot` + typed `Event`s; it never writes sim state.
- `platform.rs` is the browser seam: `wf_storage_*` (localStorage), `wf_session_*` (sessionStorage), `wf_random_u32` (crypto) imports from the miniquad plugin in `web/index.html` (files under `.wf-save/` natively), `now_ms` (pacing) and `epoch_ms` (`Date.now` stamps in saves). Save keys `orka.hero_progress.v2` and `wishfire.equipment-economy.v5`, shared with the JS game.
- `game.rs` also owns the quest system (`wf_host::progression::CombatProgression`): booted after the economy sync; each tick observes milestones before the host step, then records committed enemy defeats, drained `wave_clear_events` and queued gear collections; `claim_objective`/`train`/`spend_level_up`/`star_up` are the UI entry points. Quest save key `orka.combat_progression.v1` (numbers may serialize as `0.0` where JS wrote `0`; both load).
- `game.rs` also owns the lamp economy (`wf_host::equipment::EquipmentStorage`): synced at boot and whenever Bag receipts or gold change; every tick feeds the 15 s Bag clock. `ui/lamp.rs` is the strip (conveyor lane from off-screen left to the bag, bag count, level disc + progress), the equipment cache / review / disposal windows and the Bag upgrade window, placed by the JS CSS numbers; a lamp window pauses combat and blocks Bag progress like the JS modal gate.
- `ui/` splits by surface. Canvas (unchanged): the in-fight HUD in the JS 360x640 layout: arena band 42..430 (`camera::BAND_*` = COMBAT_VIEW), progress HUD and Summon Boss, boss HUD + stats popover, party buff row and eight hero clocks with buff badges, the lamp strip (conveyor, bag, level disc), the COT resources row and the quest objective box, plus the opening narrative scene. Canvas text is Inter Regular (`ui/text.rs`).
- Menus and overlays are page elements driven from Rust (ORKA-63bf.19). `ui/dom.rs` is the helper: each frame `Ui::web` describes the `#wf-ui` stage (placed at the 360x640 frame, `--s` = CSS px per logical px) as a `Node` tree and `Dom::render` diffs it into real elements through the generic `wf_dom_*` element bridge in `web/index.html` (create, text, attr, unattr, insert, remove, listen). The bridge is the only JS and knows nothing about the game; a click reports its element handle and timestamp to `wf_dom_event`, queued for `Ui::web_clicks` (innermost listening element per click; `Act::Stay` on a panel keeps the click from its backdrop). Keys force a fresh element instead of morphing one screen into another.
- Element trees, ids and class names are main's (ea8bc3f2), and `ui/css/*.css` are main's rules copied verbatim (first line names the source): `hero.css`, `nav.css`, `modal_close.css`, `progression.css` (Growth dialog), `quest.css` (wallet, ladder, skip / paused-battle dialogs), `lamp.css` + `bag_upgrade.css` (cache, review, dismantle, Bag upgrade), `receipt.css`. `stage.css` and `lamp_adapter.css` adapt main's `position:fixed` overlays to the stage; `quest_map.css` and `vault.css` restate screens main draws on its canvas. Art uses main's paths under `assets/` (staged by the build script, versioned with `WF_ART_REV`); SVG icons are `<img>` data URIs because the bridge creates HTML elements only.
- Menu behaviour follows main: POWER UP opens the Growth dialog over the current screen (combat pauses, no departure); a HUD party icon opens its Party Skills entry; a hero clock opens that hero's Special on the Hero screen; the entry fade is a page element above the menus. Where main measures in JS, Rust computes the same numbers: Growth stage height (`layoutClose`), gear-cell centring (`assets::gear_cells`), fanfare particle offsets. Not reproduced: focus management, scroll-into-view of a focused Party Skill, glyph-cropped close marks and stat numbers (text with a small CSS nudge instead).
- Menu parity is checked against main with `output/fable-reference/tools/compare.mjs` (Hero) and `compare-screens.mjs` (other screens) in the main checkout's output folder.
- Boot lands on the Quests map; `?qa&seed=N` boots straight into combat (`startCombatForQA`) and fixes the seed; keys 1/2/4 speed, P pause, R restart, B summons an available boss (same as the Summon Boss button). `wasm_exports.wf_app_probe(i)`: 0 step, 1 wave, 2 combat time, 3 hash low bits, 4 live enemies, 5 fps, 6 boss state (0 locked, 1 available, 2 armed, 3 active), 7 boss seconds left, 8 cleared bosses.
- Art comes from `gen/` (packed by `rust/wf_pack` from `web-runner/assets/puppets` + chapter arenas) and `web-runner/assets/rust-combat/manifest.json` (effects, decals, font). `build.rs` fingerprints both; a stale atlas fails loading with a visible message.
- Build and stage with `tools/build_wf_app.sh`; review at `tools/serve_wf_app.sh` on 127.0.0.1:8807. `gen/`, `web/gen`, `web/art`, `web/*.wasm` stay untracked.
- Tests: `cargo test -p wf_app` (needs `gen/` packed). Client scenarios run on the real host loop through `testing::HostRun` (a seeded `wf_host::Session`, level-1 party, one 30 Hz step per `step()`, last snapshot kept across attempt gaps): camera containment through the Chapter 1 boss and attack facing over 18000 steps. Two `#[ignore]`d tests are bounded crowd search tools, not gates. Retired slice-only scenarios (sim spotlight playback, Healing Spring glow, Mirewing art, the 32-High-Orc crowd pin, the boss-intro camera cut) are noted in place with their reasons (ORKA-63bf.12).
