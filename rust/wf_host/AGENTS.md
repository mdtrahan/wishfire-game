# Rust host DOX (wf_host)

## Purpose
- Translation of the JS combat host loop: `rustCombatRuntime.mjs` + `combatAuthorityDriver.mjs` + `questCombatSession.mjs` + the continuous stage runtime, as one `Session` over `simulation_core::combat_abi::World` and the `wf_meta` rules.

## Contracts
- `Session::new(seed, rows, progress, party, combat_session_id, next_uid, persist, quest)` spawns the opening wave; `tick(now_ms)` paces fixed 30 Hz steps from wall time scaled by `dev_speed`; `pause()` drops the debt; `dispose()` ends the world.
- Encounter ids are `rust:<checkpoint id>:<combat_session_id>:<n>`. The session id must be unique per boot (the app salts it with boot time); the reward outbox rejects a reused id, which is what JS avoided with `crypto.randomUUID()`.
- `progress.rs` is the `orka.hero_progress.v2` save envelope. `HeroProgressStore::from_snapshot` is `createHeroProgressStore`: every save (JS or Rust) loads through it, unknown keys and heroes drop, a corrupt checkpoint or outbox is an error with the JS message. `HeroProgress::award_exp` is `awardHeroEXP`. Hero records come in three JS shapes (fresh, normalized, `saveHeroProgress`); the oracle compares JSON values, not key order.
- `Session::new` is also `restoreHeroProgressFromStorage`: restored receipts settle before the party attaches, then a saved boss attempt is dropped, pending gold and battle rewards recover, and the configured stage checkpoint persists. `rewards.rs` is the combat reward outbox: kill rows stay pending until the next attempt settles them into `bagRewards`.
- Oracle: `tests/progress.rs` against `tests/fixtures/rust-oracle/hero_progress.json` (EXP awards, store normalization incl. legacy topology and error cases, level presets, restores of hand-made and real trace saves).
- `equipment.rs` is `equipmentStorage.mjs`: one `EquipmentStorage` over a `Storage` (localStorage) plus an optional checkpoint store (sessionStorage conveyor clock), driven through the `LampHost` trait (the session implements it: progress, gold, pending gold, live hero keys, `revise_hero`). `transact` is the JS read-modify-write: roster guard, paid-stage import, pending gold receipts, pending Bag kill receipts, conveyor clock, classify/change/classify, validate, save, `apply` (equipment stats and lamp EXP into hero records; live heroes get a permanent-input revision). No Web Lock: the Rust app is one writer. `advance_bag_clock` is combatHostClock's 15 s tick receipt.
- Live revisions (#229): `Session::queue_permanent_inputs` rebuilds a hero's permanent inputs from its saved record and submits a `replace_permanent_inputs` command with the next step; the `permanent_inputs_applied` ack (under `body.data`) must arrive in that step or the session fails like the JS driver. `tests/revision.rs` proves two successive equips reach the world.
- Battlefield orbs (ORKA-63bf.20): `EquipmentStorage::drop_orbs(count)` saves that many rolled items in `lamp.orbs` (the client decides which kills drop); `collect_orbs(ids)` picks up the named orbs in drop order and returns `OrbPickup` (ORKA-63bf.34): items that raise a hero's CP enter the Bag, never past its free slots; the others are dismantled at once and their Essence is saved in the same transaction; every picked-up item, stored or dismantled, is reported as a gear collection. Both adopt uncollected conveyor emissions of older saves as orbs. The field is bounded at `ORB_LIMIT` (40): `drop_orbs` always lands every drop and displaces the oldest orb of the lowest rarity, and `read` trims an older oversized save (`trim_saved_orbs`) before validating it. The conveyor methods remain for the JS oracle only; the app no longer calls them. `Session::spotlight` (default OFF) is the Skill Spotlight preset for the worlds the session creates, with `set_spotlight` / `release_spotlight` for the client. `Session::subwave_completions` counts completed subwaves (next subwave released, ordinary wave cleared, boss fell) for the client; no rule reads it. `tests/orbs.rs` covers drops, capacity blocking, resumed collection, dismantle Essence and chained upgrades.
- `EquipmentStorage::complete_fill(expected_fills)` settles one full Bag bar while Bag levels are frozen (`wf_meta::lamp::complete_bag_fill`); `upgrade` is kept for the future EXP-gated levels and has no caller in the game.
- Oracle: `tests/lamp_storage.rs` replays the scripted equipmentStorage transaction sequence in `tests/fixtures/rust-oracle/lamp.json` (saves, hero records, gold, receipts after every step).
- Battlefield resource drops (ORKA-63bf.33, Rust-only, temporary): `CombatProgression::grant_hero_ticket` adds one ticket to a hero that can still level and `EquipmentStorage::grant_essence` credits Essence; Gold is added to `Session::gold_total` and synced like kill Gold.
- `progression.rs` is `combatProgression.mjs`: `CombatProgression` over a `Storage`, driven through `QuestHost` (the session implements it on top of `LampHost`: live party as `QuestHero`s, stage region/boss flag, `permanent_inputs`, `apply_growth` which sets `session.training`/`stars` the way `globals.PartyTrainingLevels`/`HeroGrowth` feed the combat config). `boot` is the creation ensure + `reconcileTicketSpends` + Essence `sync`; `observe` re-ensures on the JS signature (region, boss, party levels/KO, cursor, training) or when `EquipmentStorage.generation` moved; `record`/`claim`/`record_committed_enemy_defeats`/`spend_level_up`/`train`/`star_up` commit the save and raise the JS `notify` reasons (`training`, `star-up`, `ticket-spend` revise the live party). Ticket level-ups award the saved record exactly one level (`persistHeroLevelSpend`) against the canonical key the hero screen uses; the live `<name>#1` party never reads it, which is the JS behavior (audit item for ORKA-63bf.12). Essence receipts settle through `EquipmentStorage::award_combat_essence` once each. Gear-collect events come from `EquipmentStorage::on_gear_collected` (the app queues the id and records `gear:<id>` on its next tick, so the acknowledgement is immediate rather than awaited). `dev_grant_incense` is a developer grant for the app's Dev Tools, not a game rule. No JS oracle for this glue: `tests/quest.rs` proves opening objectives, defeat recording and claiming, training reaching the Rust actor's permanent revision, a ticket level-up reaching the save and the live hero, and Essence reaching the lamp save.
- Boss flow is the JS one: final wave clear arms the boss automatically; a timeout or party wipe sets `bossSummonRequired`, ordinary waves resume, and `summon_boss(now_ms)` re-arms it.
- Trace recording (ORKA-63bf.29): the stage trace began as the JS host's recording and this host reproduced it exactly through ORKA-63bf.27. Combat rules are Rust-only, so an owner rule change re-records it from this host: `WF_RECORD_STAGE_TRACE=1 cargo test -p wf_host --test trace` (the recorder was first shown to reproduce the JS recording under the old rules). Re-recorded 2026-11-05 for the Arcane Pulse blast and the chest footprint: same outcomes (level 1 times out on the boss and recovers, level 7 clears into stage 2), different hashes and wave times. Re-recorded again for ORKA-63bf.30 (refill clocks) and ORKA-63bf.37 (fodder bomb time), same outcomes each time. Never re-record to make a failure pass.
- Parity proof: `tests/trace.rs` replays `tests/fixtures/rust-oracle/stage_trace.json` (seed 7 and seed 42 at level 7, short runs plus 17500-tick runs through all ten Chapter 1 waves: the level-1 party times out on the boss and recovers, the level-7 party clears it into stage 2) and requires identical gameplay hashes, op sequence, transitions, spawn log, boss timeout record and checkpoint.
- Wall-clock gates (`Date.now()` in JS: boss entry wipe, boss-clear tail) read the frame clock passed to `tick`; the JS harness pins `Date.now` to the same clock so the trace is deterministic.
- Regenerate fixtures with `node tools/rust_oracle/write_fixtures.mjs`; run `cargo test -p wf_host`.
